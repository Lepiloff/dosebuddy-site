**О терминологии.** Везде «профиль» и «устройство профиля», а не «мама» и не
«родитель». Роль живёт на связке (аккаунт ↔ профиль) (§1.2), у одного аккаунта
могут быть одновременно свои и наблюдаемые профили (§1.3, случай 2), и профиль —
не обязательно пожилой родственник. Формулировки, предполагающие обратное,
однажды окажутся ложью в интерфейсе.

## 0. Общие правила

**База:** `https://api.dosebuddyapp.com/v1`

**Версия в пути.** Клиент в проде и сервер эволюционируют независимо, сервер
держит совместимость с уже опубликованными сборками (§5.3). `/v2` появляется
только при несовместимом изменении; добавление необязательного поля таковым не
является.

**Авторизация:** `Authorization: Bearer <access_token>` на всём, кроме
`/auth/google` и `/auth/refresh`.

**Ошибки** — всегда один конверт:

```json
{ "error": { "code": "profile_not_found", "message": "…" } }
```

`code` — стабильная строка, на неё можно ветвиться. `message` — для логов
разработчика, не для показа пользователю: он не локализован и может измениться.
Внутренности наружу не попадают никогда (ни SQL, ни строки подключения, ни
трассировки) — см. тест `test_failure_detail_never_leaks_the_connection_string`.

Коды HTTP: `400` невалидный запрос, `401` нет/просрочен токен, `403` роль не
позволяет, `404` нет объекта либо нет доступа (различать эти два случая наружу
нельзя — иначе перебором узнаётся существование чужих профилей), `409`
конфликт состояния, `429` лимит, `503` не готов.

**Идемпотентность.** Все идентификаторы — UUID, сгенерированные на устройстве
(`SyncColumns.id`). Поэтому повтор `push` после обрыва связи безопасен: это
upsert по тому же `id`, а не второе создание.

**Время** — целое, миллисекунды UTC, как в модели устройства (`plannedAt`,
`updatedAt`). Ни строк ISO, ни локальных зон на проводе.

Исключение — поля расписания, которые по своей природе локальные и уже так
хранятся на устройстве; сервер повторяет их формат дословно, не разбирая:

| Поле | Формат |
|---|---|
| `schedules.times` | JSON-массив локального стенного времени, `["09:00","21:00"]` |
| `schedules.days_of_week` | JSON-массив номеров дней ISO, 1 = понедельник |
| `schedules.start_date`, `end_date` | ISO-8601 дата, локальная; `end_date` включительно |

Сервер их **не интерпретирует**: расписания разворачивает в дозы устройство
(§3.4), и второй реализации календарной логики на сервере быть не должно —
разойдутся.

## 1. Auth

Google Sign-In. Сервер проверяет Google ID token и выдаёт **свои** токены;
Google не становится источником сессии.

### `POST /auth/google`

```json
{ "id_token": "<google id token>",
  "device": { "id": "<uuid>", "platform": "android", "app_version": "1.1.0" } }
```

Ответ `200`:

```json
{ "access_token": "<jwt>", "expires_in": 900,
  "refresh_token": "<opaque>",
  "account_id": "<uuid>" }
```

> Ред. 4 исправляет ошибку документа: здесь стоял вложенный
> `account: { id, created_at }`, а сервер всегда отдавал плоский `account_id`.
> Прав код. `created_at` аккаунта клиенту не нужен и не отдаётся.

- Личность — Google `sub`. Email хранится (шифрованным) для поддержки, но
  **ключом не является**: email меняется, `sub` нет.
- `device.id` генерирует клиент и хранит постоянно. Смена `device.id` — это
  новое устройство со своей сессией, а не переустановка.
- Первый вход создаёт аккаунт. Отдельного «регистрации» нет.

### `POST /auth/refresh`

```json
{ "refresh_token": "<opaque>" }
```

- Refresh-токен **непрозрачный, хранится в БД хешем и ротируется при каждом
  использовании**. Самодостаточный JWT здесь не годится: «убрать опекуна» и
  «отвязать устройство» обязаны действовать немедленно, а отозвать JWT нельзя.
- Повторное использование уже ротированного токена трактуется как компрометация:
  вся цепочка этого устройства отзывается, ответ `401`.

### `POST /auth/logout`

Отзывает refresh-токен текущего устройства. Access доживает свои минуты — это
осознанно, иначе на каждый запрос нужна проверка в БД.

### `DELETE /account`

Удаление аккаунта: данные аккаунта, его устройств, членств и профилей, которыми
он владеет. **Обязательство Google Play**, появившееся вместе с аккаунтами;
нужен ещё публичный URL для тех, кто уже удалил приложение.

Профили, которые аккаунт только наблюдал, не трогаются — они не его.

## 2. Устройства и push

### `PUT /devices/{device_id}/push-token`

```json
{ "fcm_token": "…" }
```

Токен FCM меняется сам по себе; клиент обновляет его при каждом изменении, а не
только при входе.

### `POST /devices/{device_id}/sync-token`

Добавлено ред. 10 по `05i`. Решение владельца 2026-08-15.

Ответ:

```json
{ "sync_token": "<jwt>", "expires_in": 7776000 }
```

**Зачем.** Фоновая половина приложения не может пользоваться refresh-токеном:
он ротируется при использовании, а экран и фоновый воркер предъявили бы его
одновременно — сервер увидел бы повтор, счёл кражей и погасил бы все сессии
устройства. Поэтому фону сеть запретили, и цена запрета оказалась смыслом
продукта: доза, подтверждённая из уведомления или пропущенная во сне, лежала на
телефоне, пока владелец не откроет приложение. Опекун не узнавал ничего.

Этот токен существует для фоновой половины. Два свойства делают его безопасным
для долгого хранения:

1. **Область — только `POST /sync/push` и `GET /sync/pull`.** На любом другом
   эндпоинте — `403 token_scope_insufficient`, включая выдачу нового такого же
   токена. Копия не может ни передать авторитет напоминаний, ни привязать
   опекуна, ни удалить аккаунт: то есть не может ни заставить звонить чужой
   телефон, ни заставить замолчать нужный.
2. **Умирает вместе с устройством.** Отвязка действует немедленно —
   `deps.current_caller` перечитывает строку устройства на каждом запросе, эта
   проверка существовала и раньше. Хранить список выданных токенов не нужно.

**Не ротируется** — в этом весь смысл, ротация и была причиной запрета.

**Живёт 90 дней**, выдаётся повторно сколько угодно раз, и выдача нового **не
гасит старый**. Иначе устройство, которое месяцами не открывали, — а это ровно
тот случай, ради которого механизм строится, — теряло бы доступ при попытке его
обновить.

Чем платим: ротации нет, значит украденную копию в работе не заметить. Принято
осознанно. На устройстве уже лежит refresh-токен, живущий столько же и умеющий
строго больше, — эта дверь не открывается заново, она уже открыта.

Клиенту: получать из foreground, где есть обычный access-токен, хранить в
Keystore рядом с refresh, обновлять при открытии приложения ближе к истечению.

### `POST /devices/{device_id}/heartbeat`

Отметка «устройство на связи». Именно она питает сигнал `profile_stale` (§5) —
без неё «нет данных» неотличимо от «нечего сообщать».

## 3. Pairing

Код генерирует **владелец профиля**: действие по расшариванию совершает тот, чьи
это медданные — самая чистая конструкция согласия под GDPR.

### `POST /pairing/codes`

```json
{ "profile_id": "<uuid>", "role": "with_alerts" }
```

Ответ:

```json
{ "code": "K7M-2QP", "expires_at": 1754800600000 }
```

- Роль (`viewer` | `with_alerts`) выбирается **при выдаче**, не при вводе: иначе
  принимающая сторона сама решала бы, сколько ей видно.
- Код одноразовый, TTL порядка 10 минут, в БД хранится хешем.
- Выдача — **запись о согласии**: кто, какой профиль, когда, с какой ролью.
  Хранится ради accountability, а не отладки.
- Только `owner` профиля. Иначе `403`.

### `POST /pairing/redeem`

```json
{ "code": "K7M-2QP" }
```

Создаёт членство и возвращает профиль в проекции наблюдателя (§4.3). Частота
попыток ограничена: короткий код без лимита перебирается.

### `POST /profiles/{id}/reminder-authority`

```json
{ "device_id": "<uuid>" }
```

Передача авторитета напоминаний другому устройству. У профиля ровно одно
устройство материализует будильники (§1.4), поэтому это осознанная операция —
смена телефона или переезд профиля между устройствами одного аккаунта.

**Через sync push это делать нельзя, и поэтому там его нет.** Авторитет,
проходящий обычным потоком изменений, разрешался бы last-write-wins, а два
устройства, каждое из которых считает себя хозяином, — ровно то состояние,
против которого инвариант и существует. Один эндпоинт, один писатель, один
ответ.

Предыдущему устройству уходит push `reminder_authority_lost`, **но корректность
на нём не держится**. Истина — поле `owner_device_id` на профиле, которое каждое
устройство видит при ближайшем `pull`: увидев там не свой id, оно перестаёт
взводить будильники. Push лишь ускоряет это. Если бы инвариант зависел от
доставки push, потерянное уведомление означало бы два звонящих телефона по одной
дозе.

#### Тело nudge (ред. 11)

```json
{ "type": "reminder_authority_lost",
  "profile_id": "<uuid>",
  "owner_device_id": "<uuid нового владельца>",
  "revision": "214",
  "expires_at": "2026-08-18T13:00:00Z" }
```

**Все значения — строки.** Не стилистика: в FCM HTTP v1 `data` это
`map<string,string>`, и число, отправленное числом, всё равно приедет строкой.
`revision` — `"214"`, а не `214`.

| Поле | Что это | Зачем получателю |
|---|---|---|
| `owner_device_id` | новый владелец | отличить «ты потерял» от «потерял кто-то другой»: id, равный собственному, значит сообщение не про тебя |
| `revision` | `server_seq` профиля на момент передачи | сравнить с последним, что приехало по `pull`; строго не новее — отбросить |
| `expires_at` | ISO-8601 UTC, момент отправки + 1 час | вровень с TTL у FCM; сообщение, пережившее свой срок, описывает состояние, которое могло смениться |

**То же число обязано ехать по `pull`** — иначе забор мнимый: устройству не с
чем сравнивать, проверка «строго новее» пропускает любой push, и повторно
отправленный nudge способен отменить передачу, которая с тех пор была сделана
заново. См. `profiles.revision` в §4.3.

**Почему `server_seq`, а не отдельная колонка.** Он уже есть, уже монотонен и
уже сдвигается при передаче авторитета. То, что он растёт и в других случаях,
делает фильтр консервативным в безопасную сторону: передача на 205, push несёт
205; правка имени двигает до 260; устройство забирает 260 и запоминает вместе с
`owner_device_id`; опоздавший push на 205 отвергается — верно, потому что у
устройства уже более свежая правда.

**«В других случаях» — это не только правки.** `server_seq` — позиция в ленте, а
не счётчик изменений, и она сдвигается ещё и при повторной выдаче профиля: обмен
кода пары поднимает `server_seq` строкам профиля, лекарств и доз, не трогая
`updated_at` (это починка P0 от 15.08, `pairing._resend_profile`). Наблюдалось на
проде 18.08: `revision` профиля прошёл 214 → 414 при `updated_at` от 11.08.
Для правила «строго новее» это безвредно — ревизия только растёт, — но читать
`revision` как «сколько раз профиль меняли» нельзя.

**Чего это не чинит.** Nudge остаётся best-effort. Он доходит только до
устройства с живым токеном, которое сейчас забирает сообщения; для выключенного,
в глубоком Doze или force-stop оба устройства узнают о передаче только `pull`'ом,
в произвольном порядке. Замер 15.08: 49 секунд тишины либо 4 мин 36 с двойного
звона, направление решают два независимых расписания фоновых задач. Nudge делает
быстрым обычный случай, а не делает нарушение §1.4 недостижимым.

### `GET /profiles/{id}/members` · `DELETE /profiles/{id}/members/{account_id}`

Кто видит профиль и с какой ролью; отзыв — только владельцем. Отзыв немедленно
аннулирует refresh-токены устройств этого аккаунта **в части данного профиля** и
прекращает выдачу ему изменений.

## 4. Синхронизация

### 4.1 Курсор

Курсор — **непрозрачная строка**, выданная сервером. Внутри — монотонный
`server_seq`, присваиваемый сервером при записи.

Курсор **не строится на `updatedAt` устройства.** Часы на телефонах врут, а
совпадающие миллисекунды на границе выборки теряют записи навсегда и незаметно.
`updatedAt` используется, но для другого — для разрешения конфликтов (§4.4).

### 4.2 `POST /sync/push`

```json
{ "changes": {
    "profiles":    [ { "id": "…", "updated_at": 1754800000000, "deleted_at": null,
                       "name": "…", "color": 4283215696, "sort_order": 0 } ],
    "medications": [ … ], "schedules": [ … ],
    "dose_events": [ … ], "stock_events": [ … ] } }
```

#### Чего на проводе нет

Два поля исключены из синхронизации по разбору app-трека, и по разным причинам.

**`profiles.is_elder_mode`** — по собственному комментарию в коде это свойство
**устройства**, а не профиля: «this device renders the elder-mode UI for this
profile». На строке профиля оно живёт исторически, потому что в v1.0 устройство
было одно. Синхронизация разнесла бы настройку отображения одного телефона на
все устройства аккаунта: включил крупный шрифт на телефоне того, за кем следишь,
— получил его у себя.

**`medications.current_stock`** — кэш суммы журнала `stock_events`, о чём прямо
сказано в коде. App-трек предложил синхронизировать поле, но пересчитывать его на
клиенте после `pull`. Идём дальше: **не отправлять вовсе.** Производное значение
на проводе — это два источника истины, между которыми возможно расхождение;
единственный способ гарантировать, что они не разойдутся, — не иметь второго.
Клиент вычисляет остаток из журнала, сервер при необходимости сделает то же самое
из своего.

> **Следствие для применения изменений.** Поля, которых нет на проводе,
> **сохраняют локальное значение**. Применение пришедшей записи — это обновление
> известных полей, а не замена строки целиком: наивная замена обнулила бы
> `is_elder_mode` при первом же `pull`.

#### Никогда не синхронизируется

Локальное операционное состояние, к пользовательским данным не относящееся:
`scheduled_alarms`, `alarm_outbox`, `app_settings`, `materialization_revision`.

Запрет записан явно по просьбе app-трека — чтобы никто не добавил их «для
полноты». Синхронизация `alarm_outbox` между устройствами напрямую нарушила бы
§1.4: намерение поставить будильник уехало бы на устройство, которое хозяином
напоминаний не является.

Ответ:

Ответ различает **три исхода на запись**, но двумя списками: то, чего нет ни в
одном, применено — а это обычный случай, не заслуживающий строки на каждую из
тысячи.

```json
{ "cursor": "c2VxOjkxNDgy",
  "rejected": [ { "entity": "medications", "id": "…", "code": "forbidden_role" } ],
  "retry":    [ { "entity": "schedules",   "id": "…", "code": "missing_parent" } ] }
```

`rejected` — окончательно: повтор ничего не изменит, клиенту следует
остановиться и показать это. `retry` — не вина клиента (родитель ещё не доехал,
конфликт), и та же запись позже пройдёт. Свести их в один список значило бы
заставить клиента либо сдаться на поправимом, либо вечно повторять безнадёжное.

- Отправлять можно только изменения **своих** профилей. Наблюдаемый профиль
  доступен на чтение: `rejected` с `forbidden_role`, не `403` на весь запрос —
  одна лишняя запись не должна ронять весь батч.
- Батчи ограничены по размеру; лимит возвращается в `429` с `Retry-After`.

#### Правило удалений

**Ничто не исчезает с провода молча. Любое удаление — `deleted_at`.**

Первая редакция утверждала, что модель это уже умеет. App-трек показал, что для
`dose_events` это неверно: `DoseMaterializer._purgePending` физически удаляет
будущие pending-дозы при правке расписания, и без tombstone ближайший `pull`
воскресил бы то, что устройство убрало сознательно — пользователь поменял время
приёма, а старые дозы всплыли обратно.

Принят **вариант A**: пурж расписания переводится на `deleted_at`. Правка на
стороне приложения, протокол остаётся чистым.

**Retention — и здесь правило шире, чем предложил app-трек.**

Для `dose_events` независимая чистка по возрасту на обеих сторонах безопасна: от
их полноты ничего не вычисляется.

Для `stock_events` — **нет**, и это разобрано по коду. `_retentionCleanup`
сворачивает вычищаемые события в **новое** `stock_event` с суммой (baseline) и
удаляет старые физически. Если такой baseline уедет на сервер, где исходные
события ещё лежат, сумма журнала удвоится, и любое свежее устройство посчитает
неверный остаток. Отказ тихий: ни исключения, ни расхождения статусов — просто
неправильное число.

Поэтому сворачивание обязано **пересекать провод целиком**: вставка baseline
плюс `deleted_at` на свёрнутых событиях. Тогда обе стороны приходят к одному
журналу, а сервер не выполняет собственной арифметики свёртки — по той же
причине, по которой не разворачивает расписания (§0): вторая реализация той же
логики разойдётся с первой, и разойдётся тихо.

Сервер вправе физически удалять записи, у которых `deleted_at` старше 18
месяцев. Для клиентов это невидимо: свежее устройство получает уже свёрнутое
состояние.

**Свёртку выполняет только устройство с reminder-authority.**

Спека §1.1 разрешает аккаунту иметь несколько устройств, а `_retentionCleanup` —
локальный свип, который запускает то устройство, которое проснулось. Значит при
двух своих телефонах на одном профиле оба свернут журнал независимо и отправят
по своему baseline. Сумма удвоится снова — на этот раз без всякого участия
сервера.

Правило поэтому такое: **порождать** свёртку вправе только хозяин напоминаний
(§1.4); **применять** пришедшую — любое устройство. Остальные получают baseline и
надгробия по sync и вправе физически убрать у себя пришедшее удалённым, но
собственный baseline не создают никогда.

Опекунов это не касается: при статус-only `stock_events` до них не доходят
(§4.3), так что порождать свёртку им попросту не из чего.

### 4.3 `GET /sync/pull?cursor=…`

```json
{ "cursor": "c2VxOjkxNTAx", "has_more": false,
  "changes": { "profiles": [ … ], "medications": [ … ],
               "schedules": [ … ], "dose_events": [ … ], "stock_events": [ … ] } }
```

**Лимиты.** Тело — не больше **2 МБ** (nginx), записей в одной пачке `push` —
не больше **1000** суммарно по всем сущностям. Превышение отвергается целиком с
`413 batch_too_large`, а не обрезается: обрезанная пачка оставляет клиента в
уверенности, что он отправил всё, и недостающие строки замечаются потом как
данные, которые просто не доехали.

**Каждая запись несёт `op_seq`** — монотонный счётчик устройства, не зависящий
от часов. Вместе с `origin_device_id`, который сервер берёт **из токена, а не из
тела**, он образует личность операции.

Сравнение идёт по тройке `(updated_at, origin_device_id, op_seq)`, и это делает
сразу две вещи. Повтор той же операции — точная ничья: ничего не переписывается,
`server_seq` не меняется, строка не рассылается остальным устройствам. А две
правки одной строки в одну миллисекунду различимы, потому что `op_seq` у них
разный.

> **Отмена прежней формулировки.** Ред. 4 обещала идемпотентность по строгому
> «`updated_at` больше текущего». Это было неверно и теряло данные: вторая
> правка в ту же миллисекунду принималась за повтор первой и молча исчезала.
> Ошибку нашёл app-трек. Сравнение по одному лишь времени не может одновременно
> распознать повтор и различить две правки — для этого нужна личность операции.

**Причинный порядок НЕ гарантируется.** Родитель может приехать позже ребёнка,
и клиенту нужна очередь ожидающих родителей.

Причина не в лени. `pull` отдаёт текущую версию строки под её последним
`server_seq`, а не историю. Профиль, созданный первым и переименованный вчера,
имеет `server_seq` выше, чем лекарство внутри него, — и при выборке с нуля
лекарство придёт раньше профиля. Гарантировать иное можно было бы, лишь рассылая
родителей повторно, то есть сломав саму идею дельты.

Сортировать страницу по типам сущностей, чтобы «обычно» родитель шёл первым, я
сознательно не стал. Тогда очередь ожидающих срабатывала бы редко — то есть
почти не проверялась бы, а сработала в редком случае и с ошибкой. Пусть лучше
она работает всегда и потому остаётся исправной.

Записи, чей родитель ещё не приехал, `push` возвращает в `retry`, а не в
`rejected` (§4.2).

**Постраничность обязательна.** Клиент обязан крутить `has_more` до конца; сервер
режет страницу на своё усмотрение и вправе изменить её размер без bump'а версии.
Отдельного «первичного sync» нет: первый `pull` с пустым курсором отдаёт всё,
постранично. Объём конечен — retention держит историю в 18 месяцах, верхняя
оценка для тяжёлого пользователя порядка 13 тысяч `dose_events` (расчёт
app-трека).

На проводе всегда присутствуют до **трёх суток будущих `pending`-доз**:
материализатор работает скользящим окном 72 часа. Это те самые записи, которые
удаляются при правке расписания, — поэтому окно и правило удалений связаны.

**Выдача зависит от роли** — это прямое следствие решения «только статус» (§1.6):

| Сущность | Свой профиль (`owner`) | Наблюдаемый (`viewer`, `with_alerts`) |
|---|---|---|
| `profiles` | целиком, включая `owner_device_id`, `revision` и `role` | `id`, `name`, **`role`** |
| `medications` | целиком | `id`, `profile_id`, `name`, `form` |
| `schedules` | целиком | **не выдаётся** |
| `dose_events` | целиком | `id`, `medication_id`, `profile_id`, `planned_at`, `status`, `action_at` |
| `stock_events` | целиком | **не выдаётся** |

Не выдаются наблюдателю: расписания, остатки (`current_stock`, `pack_size`),
заметки, фото, пороги пополнения, а также `owner_device_id` и `revision` — какое
устройство звонит по чужому профилю его не касается, а ревизия существует ровно
затем, чтобы решать, продолжать ли взводить будильники. Наблюдатель не взводит
ни одного.

**`profiles.revision`** (ред. 11) — строка с десятичным числом, `"214"`.
Монотонна в пределах профиля, растёт при любой записи в него. Единственное её
назначение: сравнение с `revision` из push `reminder_authority_lost` (§3).
Устройство хранит последнюю приехавшую и отбрасывает push, чей `revision` не
строго больше. Строка, а не число, потому что во втором канале — FCM — тип не
наш, а сравнивать надо одно и то же значение из обоих.

**Но `role` выдаётся всем, и это вопрос P0, а не удобства.** Без неё наблюдатель
видит профиль без `owner_device_id` и не может отличить его от собственного
профиля, который ещё никто не заявил, — то есть начал бы взводить будильники по
чужим дозам. С ролью правило не имеет неоднозначной ветки:

```
role != owner                        никогда не взводить
role == owner, owner_device_id пуст  заявить авторитет, затем взводить
role == owner, id == это устройство  взводить
role == owner, id == другое          не взводить
```

Членства (`profile_memberships`) на проводе нет и не будет: наблюдателю оно
раскрыло бы, кто ещё видит профиль, а роль отвечает на единственный вопрос,
который устройству нужно задать.

**Почему расписаний нет.** Это не про экономию трафика. Без расписаний
устройству наблюдателя нечего материализовать в будильник, и инвариант §1.4
(ровно один хозяин напоминаний) держится **структурно**, а не корректностью кода
подавления. При полной репликации одна ошибка в подавлении означала бы звонок не
на том телефоне — прямой удар по P0.

Названия лекарств наблюдателю **уходят**: без них алерт бесполезен. Это
осознанный минимум, а не недосмотр (Часть 2.4).

#### Поле `roles` — куда класть строку, без догадок

Добавлено ред. 6 по запросу app-трека. Каждый ответ `pull` несёт карту всех
видимых вызывающему профилей:

```json
"roles": { "<profile_id>": "owner" | "viewer" | "with_alerts" }
```

Присутствует **всегда**, в том числе когда `changes` пуст, и не зависит от
курсора.

Зачем: строка называет свой `profile_id`, но строка самого профиля может лежать
на страницы позади — порядок по `server_seq`, и профиль, правленный полгода
назад, отсортируется далеко после сегодняшних доз. Ждать её означало бы держать
дозы в ожидании неопределённое время.

**Определять принадлежность по форме записи нельзя.** «Нет `schedule_id` —
значит наблюдаемая» неверно: у собственной дозы это поле тоже бывает пустым.
Доза, принятая вне расписания, не имеет его вовсе, и на проводе оно объявлено
`schedule_id: uuid | null`. Такой маршрут отправил бы собственные внеплановые
дозы владельца в чужую ветку и погасил бы по ним напоминания. Закреплено тестом
`test_an_owned_dose_may_have_no_schedule`.

Роль на связке — единственный авторитетный ответ, и `roles` даёт его сразу для
всех строк страницы. Тест `test_every_pull_says_which_profiles_are_whose`.

**Исчезновение профиля из `roles` — сигнал отзыва доступа, и клиент обязан по
нему удалить локальные данные этого профиля.**

Это вторая работа, которую делает карта, и она не про удобство. Отзыв членства
до сих пор выражался только тем, что строки переставали приходить, — а «перестали
приходить» неотличимо от «на той стороне тихая неделя». Данные о здоровье
оставались на устройстве опекуна после того, как согласие, под которым они были
переданы, отозвано. Молчание не может быть формой уведомления об отзыве.

Теперь профиль есть в `roles` на одном `pull` и отсутствует на следующем.
Отсутствие — инструкция удалить: наблюдаемую историю, названия лекарств, имя
профиля. Сигнал одинаково покрывает отзыв членства владельцем, удаление профиля
и удаление аккаунта владельца — во всех трёх случаях профиль просто перестаёт
быть видимым.

Тесты `test_a_revoked_profile_disappears_from_roles` и
`test_revoking_a_membership_stops_the_data`.

#### Что из этого следует для схемы наблюдателя

Таблица выше — не оптимизация, а форма данных, в которой наблюдатель их только и
получит. Локальная схема на его стороне обязана эту форму принимать, иначе
история доз у опекуна не сохранится вовсе.

Куда именно класть наблюдаемую историю — отдельная read-only таблица или та же
`dose_events` — решает app-трек: это их сторона шва. Отдельная таблица
предпочтительнее, и по их же доводу: тогда §1.4 держится структурно с обеих
сторон, материализатор сканирует `dose_events`, и чужих доз там не существует.
**Schedule-заглушки не будет** — строка, которой не соответствует ничего на
сервере, рано или поздно уедет в push и станет чужой записью в чужом профиле.

Конкретно, и это **блокирующее** требование:

1. **`dose_events.schedule_id` у наблюдателя отсутствует всегда.** Он не «иногда
   пустой» — его нет в проекции. Колонка на устройстве должна быть nullable и
   **без внешнего ключа на `schedules`**: расписаний наблюдатель не получает
   никогда, поэтому ссылаться этому ключу не на что по построению, а не по
   стечению обстоятельств.
2. **`medications` приходят в четырёх полях.** `dose_amount`, `pack_size`,
   `notes`, `photo_key`, `refill_threshold_days`, `is_active` не придут —
   значит, и они nullable, и ни одно вычисление на устройстве не вправе их
   потребовать.
3. **`profiles` приходят без `owner_device_id` и без `revision`.** Роль вместо
   первого, см. выше; второе наблюдателю не нужно ни для чего.
4. **`updated_at` и `deleted_at` наблюдателю приходят.** Проекция режет поля
   сущности, но эти два добавляются обратно всегда — без первого нет LWW, без
   второго не доедут удаления. Видно в теле §4.6 и в `_project`.
   `created_at` не приходит: он ни в чём не участвует. Нужен — скажите, поле не
   чувствительное.
5. **Наблюдаемая доза никогда не станет полной.** Владение профилем не
   передаётся между аккаунтами: `owner_account_id` проставляется по вызывающему
   и push от невладельца отклоняется `forbidden_role`. Наблюдатель владельцем не
   становится, и одна и та же доза не приедет сначала усечённой, а потом полной.
   (Роль может меняться `viewer` ↔ `with_alerts` — проекция у них одна и та же.)

Проверено на реализации app-трека 2026-08-13: `lib/core/db/tables.dart:137`
объявляет `scheduleId` как `text().references(Schedules, #id)()` — NOT NULL и
внешний ключ. При такой схеме вставка первой же строки `dose_events`
наблюдателя падает: сначала на NOT NULL, а если снять — на FK. Требование
внесено сюда именно потому, что таблица проекции сама по себе этого не говорила.

Обратное требование к серверу: набор полей проекции — часть контракта, а не
деталь реализации. Поле, добавленное в owner-строку, **не** попадает
наблюдателю автоматически; расширение проекции — изменение контракта.
Закреплено `WATCHER_FIELDS` и тестами `test_a_watcher_never_receives_schedules`,
`test_a_watcher_gets_no_stock_or_notes`.

### 4.4 Конфликты

Сервер — авторитет (§4.3 спеки). Правило: **last-write-wins по записи целиком**,
по `updated_at` устройства; при равенстве выигрывает пришедшее позже по
`server_seq`.

Не по полям: слияние по полям создаёт состояния, которых не было ни на одном
устройстве — лекарство с новой дозировкой и старой формой. Для двух телефонов в
одной семье, правящих одно лекарство одновременно, выигрыш от слияния
воображаемый, а вред реальный.

`dose_events` — не чисто append: запись создаётся как `pending` и переходит в
`taken`/`skipped`/`missed`. То же правило LWW. App-трек подтвердил: код прав,
неточен был комментарий в `tables.dart`, потерявший оговорку ТЗ §4.4.3.
Действительно append-only — `stock_events`, правки там компенсирующими событиями.

**Статус не монотонен, и сервер не вправе это предполагать.** Разрешены и
обратные переходы: `missed → pending` автоматическим свипом
`reviveMissedWithinWindow`, когда пользователь расширил окно приёма, и
`taken → pending` отменой из календаря. Откат статуса — штатное поведение, а не
признак рассинхрона; любое правило вида «более поздний статус выигрывает»
сломается на нём. Выигрывает более поздний `updated_at`, а не «более
продвинутый» статус.

**Известное ограничение: LWW опирается на часы устройства.** Курсор на них не
строится (§4.1), а конфликт-резолюшен — да. Приложение этим часам внутри себя уже
не доверяет: счётчик `materialization_revision` существует именно потому, что
перевод часов назад — реальный случай. Практически риск мал, `dose_events` пишет
один владелец профиля (§1.4). Но при двух своих устройствах телефон с уехавшими
часами будет систематически выигрывать. Записано как ограничение осознанно:
векторные часы при неподтверждённом спросе (§0.3) — не тот размен.

### 4.6 Реальные тела — снятые с работающего сервера

Ниже не описания, а **вывод `api/tools/contract_examples.py`**, который поднимает
приложение, выполняет настоящие запросы и печатает то, что реально ушло и

### 4.5 Фото упаковок — **отложено** (решение владельца 2026-08-11)

`photo_path` в модели устройства — локальный путь, на провод он не идёт (§5.2).
Форма на проводе — `photo_key`, ключ в S3; колонка в схеме уже есть, так что
включение позже миграции не потребует.

Реализация отложена, и вот на каком разборе.

**Опекуну фото не нужны вовсе** — при решении «только статус» (§1.6) они до него
не доходят, как и расписания. **Второму устройству того же аккаунта** — случай
редкий. Остаётся один настоящий сценарий: **смена телефона**, где фото сегодня
теряются, потому что `data_extraction_rules.xml` намеренно исключает
`app_flutter/photos` из облачного бэкапа Android из-за квоты в 25 МБ.

То есть по существу это не функция синхронизации, а функция **резервного
копирования** — пункт 4 scope v1.1 (§0.1), а не часть caregiver-сценария. Ни
один пользовательский путь v1.1 на ней не завязан.

Против неё сейчас работают ещё две вещи. Она требует S3-бакета и, к нему,
IAM-пользователя или роли — то есть **ключа на машине с медданными**, ровно той
работы, которой мы избегали в решениях про бэкапы и KMS. И приоритет: спрос не
подтверждён (§0.3), а функция чинит потерю картинок при смене устройства.

**Когда возьмёмся**, потребуется: узкий IAM-пользователь на один бакет (не
переиспользовать существующий ключ), два эндпоинта —

```
POST /media/upload-url  → { "photo_key": "…", "url": "…", "expires_at": … }
GET  /media/{photo_key} → 302 на подписанную ссылку
```

— и отображение «локальный путь ↔ `photo_key`» на стороне клиента. Наблюдателю
фото не выдаются ни при каком раскладе.

## 5. Алерты

Два **разных** сигнала. Сводить их к одному нельзя, и это решение владельца от
2026-08-10.

| Событие | Когда | Что означает |
|---|---|---|
| `dose_missed` | устройство профиля прислало `dose_event` со `status: "missed"`, и прошёл порог | доза **подтверждённо** пропущена |
| `profile_stale` | от устройства профиля нет heartbeat дольше порога | **неизвестно**: связи нет |

Почему не один сигнал: слать тревогу по отсутствию данных — ложные срабатывания,
после третьего их перестают читать. Не слать — настоящий пропуск останется
незамеченным ровно тогда, когда телефон выключен, а это самый тревожный случай.
Разделение честно в обе стороны: наблюдатель видит разницу между «пропущено» и
«мы не знаем».

Следствие для схемы: серверу **не нужно самому считать ожидания по
расписаниям** — о пропусках он узнаёт из `dose_events`.

### Пороги и окна

| Параметр | Значение | Где живёт |
|---|---|---|
| `dose_missed`, задержка перед отправкой | 30 мин | на связке, настраивается |
| `dose_missed`, максимальный возраст дозы | 6 ч | сервер |
| `profile_stale`, порог молчания | **36 ч** | на связке, настраивается |
| `profile_stale`, чьё молчание считается | **только `owner_device_id`** | сервер |
| `profile_stale`, частота | не чаще раза в сутки | сервер, ключ — дата |

Порог молчания был 12 часов. Телефон в Doze за ночь молчит столько при полностью
исправной работе, поэтому опекун получал бы тревогу почти каждое утро, а тревога,
которая обычно ложная, — это тревога, которую перестают читать. 36 часов
переживают ночь, выходные у родни и день без сети.

Максимальный возраст дозы — это нижняя граница детекции. Без неё первый же скан
после выдачи роли `with_alerts` поднял бы алерт на каждую пропущенную дозу за всю
историю профиля: опекун получает стену уведомлений, в которой сегодняшнее
погребено. Одно и то же окно решает, что алерт поздно слать и что его поздно
поднимать.

**`profile_stale` — advisory, и клиент обязан его так и подать.** Он означает
ровно «приложение давно не выходило на связь» и ничего больше. Формулировки вида
«телефон недоступен» или «доза пропущена» — неверны: сервер не отличает
выключенный телефон от лежащего без сети, а пропуск дозы приходит только
сигналом `dose_missed` и только со слов устройства.

Считается молчание **того устройства, которое ставит будильники**
(`profiles.owner_device_id`), а не любого устройства аккаунта владельца. Иначе
второй телефон или планшет, оставшийся в аккаунте, поддерживал бы «всё в
порядке», пока телефон, который реально напоминает, лежит выключенным — то есть
сигнал молчал бы ровно в том случае, ради которого существует. У профиля, где
авторитет не заявлен, сигнала нет вовсе: будильники не ставит никто, и это
другая беда, а не эта.

Сигнал считается по серверному факту «устройство обращалось к API» (любой
авторизованный запрос, в том числе обычный sync), а не по тому, открывал ли
пользователь экран. Пожилой пользователь может неделями подтверждать дозы прямо
из уведомлений и ни разу не зайти в интерфейс — это не молчание.

### Полезная нагрузка push

```json
{ "type": "dose_missed",    "profile_id": "<uuid>", "subject_id": "<uuid дозы>" }
{ "type": "profile_stale",  "profile_id": "<uuid>", "subject_id": "2026-08-13" }
```

Поле называется `subject_id`, а не `dose_event_id`: у `profile_stale` это дата
окна, а не доза. (До 2026-08-13 здесь было написано `dose_event_id` — документ
расходился с сервером, исправлено по факту реализации.)

**Названий лекарств в push нет.** FCM — это Google, и отправлять туда названия
препаратов значило бы выносить данные ст. 9 третьей стороне ради текста
уведомления. Клиент получает ссылку, забирает подробности по TLS и отрисовывает
локально.

### Доставка: at-least-once со схлопыванием

Изменено 2026-08-13 по внешнему ревью. Раньше запись о доставке создавалась **до**
отправки и сразу со `sent_at`: отказ FCM означал навсегда потерянный алерт, о
котором в базе было написано «доставлено». Обоснованием служил размен «лучше
потерять, чем разбудить дважды» — размена нет, потому что FCM схлопывает
сообщения по ключу.

Что гарантируется теперь:

- **Не теряется.** Отправка повторяется с backoff 1 / 5 / 20 / 60 минут, до пяти
  попыток.
- **Не звонит дважды.** Каждое сообщение уходит с `collapse_key` вида
  `"<type>:<profile_id>:<subject_id>"`. Повтор заменяет уведомление, а не
  добавляет второе. **Клиент обязан дополнительно дедуплицировать по
  `(type, profile_id, subject_id)`** — collapse работает на доставке, но
  приложение может получить оба сообщения, если первое уже было обработано.

  `profile_id` в ключе обязателен. Без него у `profile_stale`, где субъект —
  только дата, алерт про одного подопечного молча заменял бы на телефоне алерт
  про другого. Ту же ошибку содержал серверный ключ уникальности: опекун с двумя
  родителями получал один stale-алерт в сутки на двоих. Исправлено миграцией
  `0010`.
- **Не приходит поздно, но и не раньше срока.** TTL: 6 ч для `dose_missed`,
  24 ч для `profile_stale`. Тот же срок проставляется в `android.ttl` — **по
  типу сигнала, не одним числом на всё**. До 2026-08-13 в FCM уходило плоские
  6 часов для обоих: `profile_stale` FCM выбрасывал через шесть часов, сервер
  при этом уже записал `sent` и повторять не собирался, так что выключенный на
  ночь телефон не получал ничего и нигде не оставалось следа потери. Найдено
  ревью. Правило: срок у FCM не может быть короче серверного, иначе потеря
  происходит там, где сервер её не видит. Закреплено
  `test_each_signal_keeps_its_own_ttl_at_fcm`. Просроченный алерт помечается
  `expired` и не отправляется.
- **Провал виден.** Исчерпав попытки, запись переходит в `given_up` с причиной в
  `last_error`. `sent_at` заполняется только реально принятой отправкой.

Мёртвый токен (FCM 400/404) не ретраится: приложение переустановили, и повторы
жгли бы попытки, нужные живому устройству.

### Как вызвать настоящий алерт для E2E

Специального эндпоинта нет и не будет: тестовый путь, отличный от боевого,
проверяет тестовый путь. Боевой вызывается за четыре шага и укладывается в
минуту.

1. Владелец выдаёт код с ролью `with_alerts`, опекун его гасит (§3).
2. Устройство опекуна регистрирует токен: `PUT /devices/{device_id}/push-token`.
   Без него алерт создаётся, но откладывается на 5 минут — «некому сообщить» не
   считается неудачной попыткой.
3. Владелец пушит дозу со `status: "missed"` и `planned_at` в окне
   **от 6 часов до 30 минут назад**. Позже 30 минут — ещё не срок (порог связки).
   Раньше 6 часов — уже поздно (нижняя граница детекции, §5).
4. Ждать до 60 секунд: воркер сканирует раз в минуту.

`profile_stale` вызвать сложнее — нужно, чтобы устройство владельца не обращалось
к API 36 часов. Для проверки маршрутизации проще послать себе `dose_missed`:
форма payload у них одинаковая, различается только `type` и смысл `subject_id`.

Что должно получиться: **ровно одно** уведомление на телефоне опекуна. Повторный
прогон с тем же `dose_event.id` не должен дать второго — ни сервер его не
отправит (ключ уникальности), ни клиент не покажет (дедуп по
`(type, profile_id, subject_id)`).

### Что означает `sent`, и чего оно не означает

**`sent` = FCM принял сообщение. Не «опекун увидел».**

Между этими двумя вещами лежит целиком клиентская сторона, и она уже один раз
оказалась пустой: сообщения приходили, но приложение маршрутизировало все входящие
push в обработчик смены владения, так что `dose_missed` и `profile_stale`
молча пропадали. С сервера это выглядело безупречно — все алерты `sent`, ни
одного `given_up`. Найдено ревью 2026-08-13.

Отсюда правило: серверная статистика доставки **не является** свидетельством
того, что алерты работают. Единственное свидетельство — E2E на живом телефоне.

Три вещи, о которых клиенту надо знать, и все три способны выглядеть как
«сервер не прислал»:

1. **Push может обогнать данные, на которые ссылается.** Воркер сканирует раз в
   минуту и шлёт сразу; наблюдатель тянет `pull` по своему расписанию. Поэтому
   `dose_missed` с `subject_id` вполне может прийти **раньше**, чем доза с этим
   `id` попадёт к наблюдателю.

   Уведомление обязано показываться **не имея ни строки дозы, ни имени
   профиля**. Имя тоже может отсутствовать: опекун, только что погасивший код,
   получит алерт раньше, чем к нему приедет строка профиля. (Правка 2026-08-13:
   здесь было сказано «текст берётся из типа сигнала и имени профиля» — неверно
   ровно в этом случае, и указано ревьюером.)

   Отсюда лестница, а не одна формулировка:

   | Что есть локально | Что показывать |
   |---|---|
   | ничего, кроме `type` | общий текст по типу сигнала |
   | имя профиля | то же, с указанием, о ком речь |
   | доза и лекарство | точная формулировка, уже в приложении |

   Нижняя ступень обязана существовать и обязана быть осмысленной сама по себе.
   Ждать данных — значит не показать ничего, а это и есть тот отказ, ради
   предотвращения которого весь механизм построен.
2. **Payload не несёт текста, и это не оплошность.** Ни названия лекарства, ни
   готовой формулировки — см. выше про ст. 9. Текст уведомления пишет
   приложение, локально, из того, что у него уже есть.
3. **Data-only сообщение не доставляется приложению, которое пользователь
   force-stop'нул**, и фоновые data-сообщения Android квотирует. `priority:
   high` ставится, и это всё, что можно сделать со стороны сервера. Уйти от
   ограничения можно только `notification`-payload, то есть отправив текст про
   лекарства через Google, — на что мы не пойдём. Ограничение принимается
   осознанно и должно быть известно, а не обнаружено.

## 6. Схема Postgres

Зеркало device-модели плюс то, чего на устройстве не было. Все таблицы несут
`server_seq bigint` (курсор) и `updated_at`, `deleted_at` из `SyncColumns`.

**Новое, серверное:**

```
accounts             id, google_sub UNIQUE, email_enc, created_at, deleted_at
devices              id, account_id, platform, app_version, push_token,
                     last_seen_at, created_at, revoked_at
refresh_tokens       id, device_id, token_hash, expires_at, rotated_from, revoked_at
profile_memberships  id, profile_id, account_id, role, created_at, revoked_at
pairing_codes        id, profile_id, issued_by, role, code_hash, expires_at,
                     redeemed_at, redeemed_by
```

**Зеркало устройства:** `profiles`, `medications`, `schedules`, `dose_events`,
`stock_events` — поля один в один с `tables.dart`, плюс `profiles.owner_account_id`
и `profiles.owner_device_id` (хозяин напоминаний, §1.4).

**Шифруются** (`bytea`, префикс с версией схемы шифрования):
`accounts.email`, `profiles.name`, `medications.name`, `medications.notes`,
`medications.dosage_text`.

**Не шифруются:** времена, статусы, `server_seq` — иначе сервер не определит
пропуск дозы и алерты перестанут работать. Это осознанная граница, а не
недоделка.

Блоб с версией схемы заложен сразу: переход на клиентское шифрование позже
станет сменой владельца ключа, а не миграцией схемы.

**Бэкапы.** Ночной дамп в S3, шифрованный, с регулярной проверкой
восстановления. Бэкап, который ни разу не разворачивали, бэкапом не является.

## 6a. Требования к клиенту

Из работы app-трека над SQL CHECK v6. Вносятся в контракт, потому что это
свойства **провода**, а не их внутренней схемы.

**1. Проверка `isFinite` при десериализации, до записи.** Схема здесь не спасает:
SQLite хранит NaN как NULL, а в `current_stock` и `pack_size` NULL **несёт
смысл** — «учёт выключен», «размер пачки неизвестен». Пришедший NaN молча
выключит функцию, и никакой CHECK этого не отличит. Отбраковка обязана стоять в
разборе, до записи. (`current_stock` мы из синхронизации убрали, но `pack_size`
остаётся, и правило общее.)

**2. Нарушение CHECK не роняет клиент.** Запись, не прошедшую ограничение, клиент
карантинит и продолжает — не падает и не встаёт в цикл повторов. Одна плохая
запись не должна останавливать синхронизацию остальных.

**3. Перечисления и версии.** Сервер не расширяет перечисления без bump'а версии
API; клиент карантинит неизвестные значения.

> Уточнение по механике риска. Сервер сам новых значений не изобретает — он
> зеркалит устройство. Значит опасность не «сервер прислал новое», а **более
> новый клиент прислал значение, которого не знает более старый**, и сервер его
> добросовестно передал. Фильтровать по версии клиента сервер не будет: это
> потребовало бы знать поддерживаемый набор каждой сборки. Поэтому карантин на
> клиенте — не подстраховка, а основной механизм.

**Одно следствие сверх их ответа, и это порча данных, а не сбой протокола.**
Вариант A закрывает пурж расписания, но не retention. `_retentionCleanup`
сворачивает вычищаемые `stock_events` во **вставку нового** события с суммой и
физически удаляет исходные. Независимая чистка «по возрасту на обеих сторонах»,
как предлагал ответ, привела бы к тому, что baseline уехал бы на сервер, где
исходные события ещё лежат, — сумма журнала удвоилась бы, и свежее устройство
показало бы неверный остаток. Молча: ни ошибки, ни расхождения статусов, просто
неправильное число.

Поэтому свёртка целиком пересекает провод: вставка baseline плюс `deleted_at` на
свёрнутых. Для `dose_events` независимая чистка по возрасту остаётся допустимой —
от их полноты ничего не вычисляется.

## 9. Состояние по свёртке retention

Закрыто ред. 3. App-трек взял правку на себя одним изменением: soft delete в
`_purgePending`, свёртка через `deleted_at` с исправленным запросом, вторая
ступень ретеншена и тесты на два последовательных прогона.

Их разбор добавил два следствия, которых не было в моём требовании, и оба
проверены по коду:

**Запрос свёртки не исключает уже удалённые события.** Фильтр — только по
`createdAt`. Сегодня это спит, потому что `stock_events` никто не помечает
удалёнными. Но лечение вводит ровно это, и следующий прогон свернул бы уже
свёрнутое, вставив второй baseline поверх первого. То есть исправление
воспроизвело бы ту же болезнь локально, без всякого сервера.

**Надгробия останавливают чистку доз.** Дозы удаляются только те, на которые не
ссылается ни одно выжившее `stock_event` — внешний ключ, `foreign_keys=ON`.
Запрос ссылок (`doseEventId.isNotNull()`) фильтра по `deleted_at` не имеет, так
что надгробия удерживали бы свои дозы вечно: ретеншен доз тихо перестал бы
работать, таблица росла бы без предела, ошибки не было бы. Отсюда вторая ступень:
через 18 месяцев свёртка с `deleted_at`, ещё через месяц — физическое удаление
надгробий, которое и разблокирует чистку доз. Месяц нужен, чтобы надгробие успело
доехать до сервера.

**Третье следствие — со стороны контракта, см. §4.2:** порождать свёртку вправе
только устройство с reminder-authority. Иначе два своих телефона на одном профиле
свернут журнал независимо и дадут ту же удвоенную сумму без участия сервера.

Порядок: app-трек делает это после SQL CHECK v6 — обе задачи трогают одну
арифметику остатков, и менять их одновременно значит лишиться возможности понять,
что сломалось. Ни то, ни другое не блокирует auth и pairing, которые уже в проде.

потому что каждый из них уже был однажды закрыт «в принципе».

| # | Пункт | Состояние |
|---|---|---|
| 1 | Гейт напоминаний читает `role`, а не `profile_memberships` | ✅ закрыт |
| 2 | `dose_events.schedule_id` nullable и без FK; наблюдаемая история отдельно | ✅ закрыт (`observed_doses`) |
| 3 | Маршрут входящих строк по `roles`, а не по форме записи | ✅ закрыт |
| 4 | Удаление локальных данных профиля, пропавшего из `roles` | открыт |
| 5 | **Caregiver-алерты не показываются на телефоне** | **блокер** |

**№5, найдено ревью 2026-08-13.** Приложение маршрутизирует все входящие push в
обработчик смены владения (`handleOwnershipPush` в foreground,
`ownershipPushBackground` в фоне). Типов `dose_missed` и `profile_stale` в
приложении нет вовсе, локального уведомления нет, дедупа нет. Сервер отправляет
их исправно и помечает `sent` — то есть **со стороны сервера всё выглядит
безупречно**, а телефон опекуна не показывает ничего. Требование v1.1 о
caregiver-алертах не выполняется.

Что нужно на их стороне:

1. Развести маршрутизацию команд владения и caregiver-алертов по полю `type`.
2. Записывать ключ дедупа `(type, profile_id, subject_id)` **до** показа, durable.
3. Показывать локальное уведомление, **не обращаясь ни к локальной строке дозы,
   ни к имени профиля** — push может обогнать и то, и другое, см. §5, «Что
   означает `sent`». Подробности подтягивать позже, в authenticated foreground.
4. Отдельный notification channel для caregiver-алертов — **не тот, что у
   напоминаний о пополнении**. Это разные адресаты и разная срочность, а общий
   канал означает, что отключив одно, пользователь молча отключает другое.
5. E2E: сервер → payload → обработчик → одно уведомление; повтор второго не
   создаёт.

Маршрутизацию входящих строк вести по `roles`, а не по наличию `schedule_id`
(§4.3): у собственной внеплановой дозы этого поля тоже нет.

4. **Удаление локальных данных профиля, исчезнувшего из `roles`** (§4.3).
   Отзыв согласия обязан доходить до устройства опекуна, а не выражаться тем,
   что строки перестали приходить.

Реальный sync не включается, пока app-трек не закроет долги §3.1 и SQL CHECK v6 —
по §0.5 п.7 сервер идёт впереди клиента, что и произошло.
